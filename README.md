# dsh-session-relay · 驿传

> **驿传** —— 让 DSH 里同一工作区的会话互相派工与回报。

让 [DSH](https://github.com/deepseek-ai/deepseek-harness)（DeepSeek Harness）里**同一工作区的会话互相派工与回报**：一个会话把任务卡直接发给另一个会话，对方立即开工，回报也直接发回来。**你不用再在窗口之间复制粘贴。**

```
指挥会话 ──dispatch_card(card_path)──▶ 后端窗口 inbox ──▶ 立即起一轮，开始干活
    ▲                                                        │
    │◀──── 自动投递回执（写回指挥自己的日志，不唤醒、不占轮次）    │
    │                                                        │
    └────────── 窗口干完后 send_session_message(to:"指挥") ◀────┘
```

零运行时依赖 · MIT · 单文件插件 · 83 个测试

**为什么叫「驿传」**：驿传是中国古代的接力传书体系——文书逐站传递、**每站交接须回执**，
与本插件的机制逐点对应：会话之间接力传递任务卡、每次投递自动写回执、按稳定"站名"
（角色）寻址。`relay` 一词本身也是"接力传递"，中英两名的语义是一致的。

> 说明：`驿传` 是**中文名/显示名**。npm 包名与 cordis 插件 id 保持 ASCII
> （`dsh-session-relay` / `session-relay`），因为包名与配置 id 不接受非 ASCII 字符。

## 为什么需要它

用 DSH 做多角色协作时，常见分工是：一个**指挥**会话负责拆任务、写派工单（下称"卡"），另开若干**实施窗口**（前端/后端/测试…）各自干活并回报。

这些窗口是**普通 DSH 会话**，彼此之间原本没有任何通道。于是流程退化成人工搬运：

```
指挥写好卡 → 你复制 → 切到窗口粘贴 → 窗口干活 → 你再去各窗口收回报
```

你被夹在中间当"人肉消息总线"。本插件去掉这层搬运。

### DSH 已有机制为什么不够

| 机制 | 作用域 | 为什么不够 |
|---|---|---|
| `ctx.subagents.sendMessage()` | 仅"直接父子" | 非相邻目标直接抛 `UNAUTHORIZED` |
| `ctx.agentTeams.sendMessage()` | 同一 Lead 的成员 | 实验性（`private: true`），且要求同属一个 Team |
| `session/prompt`（HTTP） | 任意会话 | 是浏览器/宿主驱动的接口，**模型自己调不到** |

即：**投递机制早已存在，缺的是"面向模型、以工作区为作用域、能按稳定角色寻址"的门面。** 本插件就是这层门面，不引入任何新传输。

## 安装

### 前置条件

- 一个可用的 DSH 安装（`~/.dsh` 下有 profile）
- DSH 里装载了 `@deepseek-ai/dsh-api-session-controller`（**web profile 默认有**；它提供跨会话投递能力）
- Node.js ≥ 20（仅开发/测试需要；运行时用的是 DSH 自带的 Node）

### 方式一：作为 DSH bundle 安装（推荐）

```bash
dsh plugin --profile web add github:YZ-max0/dsh-session-relay
```

本仓库按 DSH 官方插件形态打包（`package.json` 的 `dsh.bundle.patch` 指向 `cordis.patch.yml`），所以这条命令即可。安装后重启 DSH，或让 profile 的 `patchReload: live` 自动热重载。

### 方式二：本地 checkout（不安装 npm 包）

适合"改代码即时生效"的开发场景。把插件文件放在任意位置，然后在 profile 的 patch 文件里**用绝对路径**引用：

```yaml
# ~/.dsh/profiles/<profile>/cordis.patch.yml
- insert:
    - id: session-relay
      name: '/abs/path/to/dsh-session-relay/session-relay.mjs'
```

本仓库自带脚本替你写这一行（会备份、幂等、可卸载）：

```bash
python3 install.py --dry-run      # 先看会改什么
python3 install.py                # 安装到 web profile
python3 install.py --profile headless
python3 install.py --uninstall
```

> **为什么这个方式用绝对路径**：patch 行里**相对** `name`（如 `./x.mjs`）锚定的是**该 patch 文件所在目录**；绝对路径不受位置影响，插件源码可以留在工作区里正常编辑和版本管理，也不会产生"profile 里那份副本与源码不同步"的隐患。
>
> 另外，插件是**零裸导入**的单文件（只依赖 `node:` 内建模块）。宿主加载插件模块时按其**自身位置**解析 `import`，而插件目录不一定有 `node_modules`——零依赖设计让它放在任意路径都能加载。

## 快速上手

**第 1 步 — 每个窗口登记一次角色**（各自会话里说一句）：

```
登记角色：后端窗口
```

前端/测试/指挥窗口同理（`前端窗口`、`测试窗口`、`指挥官助理`）。角色的意义见[设计要点](#为什么需要显式登记角色)。

**第 2 步 — 一键派卡**（指挥会话）：

```
把 cards/2026-03-01-派工单-重构解析链（后端窗口）.md 派出去
```

指挥会调用 `dispatch_card({ card_path: "…" })`——**目标从文件名读出来，不用指定窗口**。对应窗口立即开工，指挥的日志里出现一条「已送达」回执。

**第 3 步 — 回报**（窗口会话）：

```
send_session_message({ to: "指挥官助理", card_path: "cards/2026-03-01-回报-重构解析链.md" })
```

> ⚠️ 回报件若沿用卡的命名法（括号里写**自己**的角色），`dispatch_card` 会推导成它自己。
> 回报方向需要显式给 `to`。见[命名约定](#dispatch_card--一键派卡)。

## 四个工具

### `dispatch_card` — 一键派卡

参数 `{ card_path, to?, message?, mode?, expect_receipt? }`。

**目标默认从文件名末尾括号推导**：

| 文件名 | 推导出的目标 |
|---|---|
| `2026-03-01-派工单-重构解析链（后端窗口）.md` | `后端窗口` |
| `2026-03-01-回报-重构解析链（后端窗口·20260302）.md` | `后端窗口`（自动剥掉 `·日期`） |
| `2026-03-01-回报（20260302）.md` | **无目标** → 报错，要求指定 |

解析规则**刻意保守**：只认文件名**末尾**括号内、**最后一个 `·` 之前**、且以「窗口」结尾的那段。

为什么不做模糊匹配——真实反例：

```
T-142-派工单-后端缺口复核（前端窗口）.md
         ↑ 标题写着"后端"                ↑ 目标只有这里说了算
```

按"文件名里出现了'前端'/'后端'"匹配，这张卡会**送错窗口**，而且失败是静默的（错的窗口开始干别人的活）。**位置**（末尾括号）是唯一可信信号。

约定不合你意也没关系：**传 `to` 即可覆盖**，无需改代码。

结果里附带 `cardReadableFromHere`：多文件系统环境（容器/跨平台挂载）里，同一份卡在不同侧可读性可能不同。它只是**提示**——`false` 表示"发送方自己读不到这张卡，别指望它复述内容，让收件方从自己那侧读"，**不会阻断投递**。

### `register_session_role`

参数 `{ role, description? }`。

- 作用域限于**本工作区**（按 `cwd` 分区），不泄漏到别的工作区；
- 重复注册同一角色 → **替换**前一个持有者；
- 一个会话只保留**一个**角色（注册新角色会释放旧角色名）；
- 寻址时做"去空白"级归一化比较（`后端窗口` 与 `后端 窗口` 视为同一个）。

### `list_workspace_sessions`

参数 `{ query?, limit? }`。返回每个会话的 `sessionId / role / title / status / createdAt / parentSessionId`。
`status` ∈ `running | idle | cold`。**有角色的排在前面**（它们才是可稳定寻址的目标）。

### `send_session_message` — 底层发信

派卡之外的自由通信（回信、追问、回报）。

| 参数 | 说明 |
|---|---|
| `to` | **角色名**或精确 session id |
| `message` | 正文 |
| `card_path` | 可选：要让对方先读的文件 |
| `mode` | `queue`（默认，立即起新 turn）/ `steer`（插到最近的 step 边界） |
| `expect_receipt` | 是否写回执，默认 `true`（对回执本身忽略） |

**为什么推荐传 `card_path` 而不是把卡粘进 `message`**：卡动辄几百行，粘贴既撑爆消息体，又产生"文件与消息两份内容谁是准"的问题。传路径让**文件保持唯一真相源**。

**语义边界**：调用只保证"**被接受**"，不等对方干完。对方的**实质回报**会作为一条新消息稍后到达，而不是这次调用的返回值。

## 设计要点

### 复用而非新造

没有发明任何底层能力，全部复用既有接口：

| 需要的能力 | 复用的接口 |
|---|---|
| 注入消息 | `Agent.followup()` / `Agent.steer()`（浏览器提交消息走的就是这两个） |
| 目标解析（含冷会话恢复、越权拒绝） | `ctx.sessionController.resolveAgent()` |
| 会话清单（含已持久化但未激活的冷会话） | `ctx.sessionQuery.listSessions()` |
| 消息归属标记 | `MessageSourceMap` 合并扩展 + `form: 'relay'` |

`resolveAgent()` 尤其关键——它一次性完成三件本来要自己写的事：活会话直取、**冷会话从持久化恢复**（并管好生命周期）、子代理拥有的会话返回稳定错误。

### 消息归属：借 `form: 'relay'` 白拿正确的 UI 呈现

转达消息构造成：

```js
{
  role: 'user',
  content: [{ type: 'text', text: '[派工/消息] 来自同一工作区的会话 …' }],
  source: { kind: 'session-relay', form: 'relay', senderSessionId: '<发送方 id>' },
}
```

`form: 'relay'` 是 DSH **既有**的 `ContextForm` 语义值，定义就是"一条别的 agent 发给这个 agent 的消息"。三个字段换来：

- Web 端用它现成的 `RelayBody` 渲染出"来自会话 X"，**客户端零改动**；
- 收件方模型能看见内容，但这条消息**不会被误记成人类指令**；
- 直接通过持久化校验。

### 自动回执用 `form: 'notice'`，并且写回发送方

回执是**运行时**对"投递已发生"的记录，不是收件方说的话，所以用 `notice` 而非 `relay`（DSH 本就区分这两者）。它写进**发送方自己**的日志，用 `inject`（`wakeup=false`）注入，因此：

- 不会打断发送方正进行的那一轮；
- 不会引发新的模型轮次（不额外烧 token）。

### 为什么必须显式登记角色

会话标题由**首条消息自动生成**，不是稳定名字。同一个"后端窗口"，标题可能是 `测试窗口`、`后端缺口复核派工单`、`指挥1.0 (1)`……

指挥没法可靠地"发给后端窗口"。所以角色必须显式登记一次——**插件故意不自动识别**：猜错会把卡送到错误的窗口，代价远大于多问一句。

### 环路安全：为什么不是"限深"

这是设计里最容易做错的地方。两个方向的要求是**矛盾的**：

- 一方面，真实协作是**指挥 ↔ 窗口长期往返**（发卡→回执→再发卡→回报）。任何"接力链深度上限"都会在**第 3 轮把正常流程拦死**。
- 另一方面，"发完即自动开跑"意味着两个 AI 会话可以互相唤醒、**在无人看着时持续烧 token**——一句「好的」被回一句「收到」就能无限循环。

采用的判据是：**自最近一条真人消息以来，连续的会话间消息条数**，上限 `MAX_AGENT_HOPS = 16`。

| 情形 | 行为 |
|---|---|
| 真人的一次输入 | **重置**预算 ⇒ 正常多卡协作完全不受影响 |
| 全是 agent 之间往复 | 累积，到 16 跳被掐断并提示回报用户 |
| 消息本身是回执 | **永不触发回执**（唯一的绝对环路不变量） |

## 安全边界

| 边界 | 规则 |
|---|---|
| **作用域** | 只允许与调用方 `cwd` **完全相同**的会话（即"同一工作区"）。`cwd` 缺失一律拒绝——无法证明同源 |
| **子代理** | 发送方 `origin === 'subagent'` 时拒绝，并指引它用 `send_message` 回报父代理 |
| **自环** | 拒绝向自己发送 |
| **角色归属** | 角色只在**注册它的工作区**内可解析 |
| **环路** | 回执不触发回执；无人介入的往复在 16 跳内掐断 |

关于**子代理判别**为什么只用 `origin` 而不用 `parentSession`：**fork（分叉）出来的普通会话同样带 `parentSession` 血缘**，用它会把 fork 会话误判成子代理。判别 `origin === 'subagent'` 才准确。

插件只读写一个角色名册文件（默认 `$DSH_HOME/session-relay/roles.json`，原子写）；**不读环境变量、不发网络请求、不改任何既有工具的行为**。

## 已知限制

1. **同进程**。注册表（`ctx.sessions` / `ctx.agents`）是进程内内存映射，插件只在**同一个 DSH 宿主进程**内工作。这是 DSH 自身的限制（见其 `subagent` 文档的 "Process-local residency"）。
2. **角色名册是机器级文件**，会话删除后条目**不会自动清理**（无害：寻址时会明确报"会话不存在"）。可手工编辑该文件。
3. **冷会话会被激活**。给冷会话发消息会把它从持久化恢复成活 Agent，占用内存——这是 `resolveAgent()` 的既有语义（浏览器打开会话也一样）。
4. **不排队重试**。投递是"当下就投"，宿主重启不补投。需要跨重启的可靠投递，应参照 DSH 的 `agent-team` mailbox 模式。
5. **回执只表示"已送达"，不表示"已被理解"**。真正的"已收卡"回信仍由收件窗口自己发出（消息里已附回信指引）。
6. **派工与回报的命名方向不对称**。卡上的括号标"这卡给谁"，回报上标"谁写的"，所以窗口回传回报需显式 `to`。当前不自动翻转——自动翻转会把"指挥自己写的回报草稿"也发错。
7. **`cardReadableFromHere` 只是提示**，不是投递门槛；插件不做跨侧取件或解密。

## 开发

**零依赖**：运行时不需要任何 npm 包，测试只用 Node 内置的 `node:test`。CI 因此不需要网络，也不会因 `@deepseek-ai/*` 发新版本而变红。

```bash
npm test          # 78 个测试
npm run check     # 静态一致性检查 + 私有信息扫描
```

### 测试怎么组织的

| 文件 | 覆盖 |
|---|---|
| `tests/target-role.test.mjs` | 文件名→目标的推导规则。**风险最高的一块**：判错会把卡静默送错窗口，所以既钉住该接受的，也钉住**必须拒绝猜测**的 |
| `tests/session-relay.test.mjs` | 角色注册、寻址、投递、回执、四条越权、失控边界、清单 |
| `tests/helpers.mjs` | 一个**假 DSH 宿主**，模拟插件真正接触的那几个面（`ctx.get`、`ctx.tools.register`、`Agent.followup/steer/inject`） |

假宿主刻意**不**重实现 schema 校验、消息冻结、inbox 语义——测试断言的是插件自身行为；真实 DSH 契约另有集成验证。

### `npm run check` 在防什么

工具的 JSON Schema 是**手写**的，而 DSH 工具注册表在**装载时**才校验它。一个漏在属性里的 `required: true`（那是 `defineTool` 的写法，DSH 会拒绝）**既过得了 `node --check`，也过得了单元测试**——只在用户装载插件时才炸。

`scripts/check-manifest.mjs` 因此静态校验：schema 关键字合法性、顶层 `required` 数组、每个 object 都声明 `additionalProperties`、插件是函数插件形态（命名导出且**无 default**，否则 DSH 会丢掉 `inject`）、`dsh.bundle.patch` 指向真实文件，以及**扫描私有信息泄漏**（本机绝对路径、内网地址、硬编码凭据）。

### 目录结构

```
session-relay.mjs        插件本体（零裸导入，可放任意路径加载）
cordis.patch.yml         DSH bundle patch（官方安装形态用）
install.py               本地 checkout 的安装/卸载脚本
package.json             包元数据 + dsh.bundle 声明
tests/                   node:test 测试 + 假宿主
scripts/check-manifest.mjs  静态一致性检查
```
